\section{Experimental Evaluation}
\label{sec:benchmarks}

The evaluation answers five questions, and each table below is labelled with the one it addresses.

\begin{description}
\item[Q1 (correctness).] Is the state identity exact (two states identified if and
only if they are isomorphic) on every workload in the corpus, checked against an independent
oracle? (Table~\ref{tab:t1-exactness})
\item[Q2 (cost against the reference).] How does evolution time compare with the Wolfram
implementation computing the same object, and how does that ratio behave with depth?
(Table~\ref{tab:t2-speedup}, Figure~\ref{fig:speedup})
\item[Q3 (parallel scaling).] How far does evolution scale with worker count, does that limit
depend on the rule, and what resource sets it? (Tables~\ref{tab:t8-scaling},
\ref{tab:t12-shapes}, \ref{tab:t13-memory}; Figure~\ref{fig:scaling})
\item[Q4 (device).] Where is the GPU faster than the CPU, and at what grid size does the device
saturate? (Tables~\ref{tab:t7-gpu}, \ref{tab:t7b-gpu-corpus}, \ref{tab:t11-saturation})
\item[Q5 (attribution).] Which contributions account for the performance, and does any of them
change the computed answer rather than its speed? (Tables~\ref{tab:t9-ablation},
\ref{tab:t6-quotient}, \ref{tab:event-canon})
\end{description}

Every table below is generated by a measuring script, and the generated table source records the commit and machine it was produced on in a provenance line; the one exception is Table~\ref{tab:device-occupancy}, transcribed from an Nsight Compute session because its reports are not text. Captions carry a \textbf{T}$n$ identifier alongside the float number: \textbf{T}$n$ names the generated fragment and ties the table to the script that wrote it, while the float number is LaTeX's; the two do not correspond, and the \textbf{T} sequence has gaps where a fragment was retired. Numbers are medians over repeated runs in one session; a comparison between two arms is always taken in the same session, because this machine's run-to-run drift exceeds most of the effects being reported.

\subsection{Experimental Setup}

\begin{description}
\item[Hardware:] AMD EPYC 9174F (16 cores, 32 threads, one socket), 503\,GB RAM, NVIDIA RTX 4090 (24\,GB, compute capability 8.9), on bare metal. The cores are homogeneous, so a speedup column divides by a comparable quantity. Workers are placed by the engine's own topology-derived order (each last-level-cache domain's cores and their SMT siblings filled before the next domain is opened, read from the cache topology at start-up on either operating system), which is the placement every user of the engine gets; each table's provenance line names the machine and the load at the moment the measurement started. A table moved to another machine carries that machine with it. The Wolfram comparison of Table~\ref{tab:t2-speedup} is the only measurement not on this host: it needs a licensed kernel, and its provenance line names the machine it was taken on. The tables and figures were not all produced by one invocation and their provenance lines name several commits, but that spread is bookkeeping rather than a difference in what was measured: no file under the engine's own source directories differs between any of those commits and the one this document was built from.
\item[Software:] Ubuntu 24.04, Linux 6.8, GCC with C++20, CUDA 12.0, Wolfram Language 14.3.
\item[Workloads:] A rule-type corpus of 17 workloads (single/multi rule; productive, idempotent, reductive, and mixed-arity rules; several initial-state shapes), plus larger depths of the canonical Wolfram rule $\{\{x,y,z\}\} \to \{\{x,y,w\},\{y,z,w\}\}$ for the scaling and GPU curves.
\item[Methodology:] Wall-clock figures are medians over repeated runs on an otherwise idle machine, with the workers placed by the engine's topology order over the host's homogeneous cores; a run taken while the machine was loaded is marked in the table's provenance line rather than published as though it were quiet. Counts, instruction-level measurements and \texttt{getrusage} figures are deterministic and are reported from a single run. One exception is stated where it applies: the left-hand-side sweep of Figure~\ref{fig:lhs-scaling} reports the \emph{minimum} of its repeats rather than the median, because contention can only make a run slower, so the minimum is the estimate interference cannot inflate; that sweep admits a timed run only after checking the machine is quiet.
\end{description}

\subsection{Correctness and Memory Footprint (Tables T1 and T3)}
Correctness comes first because a performance number for a wrong answer is not a result. Every
workload in the corpus is evolved in \textsc{Full} (exact) mode, single-threaded, to the depth
recorded with it (chosen so the brute-force cross-check stays tractable, so counts are
comparable down a column and not across rows), and its canonical state set, event set, causal relation and branchial
relation are compared against the independent reference implementation. The \emph{Exactness}
column must read \textsc{Exact} for every row, checked against the brute-force isomorphism
oracle; all seventeen agree exactly.
Table~\ref{tab:t3-deheap} then reports what those runs cost in memory, with arena bytes taken
from the arena's own byte counter rather than RSS because that figure is deterministic and
reproducible, and what they cost the global allocator, which is the claim the arena exists to
support: the measuring tool counts every call to global
\texttt{operator new} during the measured evolution, and allocations per event fall by nearly
five orders of magnitude, from $456$ to $0.007$, from the smallest runs to the largest. The count is fixed set-up performed
once per run, divided by an event count that grows while it does not; per-event allocation is
served from the arena rather than the allocator. No before/after comparison is given for the
contributions that produced this figure: each replaced path was deleted in the commit that
replaced it, the work spans dozens of commits, and the instrument that measures arena bytes did
not exist at the start of that sequence, so two numbers from two different instruments would
not constitute a comparison.

\subsection{Wall-Time Speedup (Table T2)}
The timed comparison is against the \texttt{Wolfram/Multicomputation} \texttt{MultiwaySystem},
the published implementation this engine reproduces. The reference implementation
(Section~\ref{sec:background}) enters as the correctness oracle:
its state and causal-edge counts must equal both sides' at every depth for the row to stand,
and they do; its wall time is not reported. Over depths four
to seven the engine's core is between $\SpeedupAtLowDepth\times$ and $\SpeedupAtHighDepth\times$ faster
than \texttt{MultiwaySystem}, and the ratio rises monotonically across those four depths. The
range starts at depth four because the two shallower rows are not measurements of the same thing:
depth two carries the Wolfram side's one-time initialization, and at depths three to five the
engine's own time is a fraction of a millisecond, close enough to the timer's resolution that those ratios
are lower bounds on the gap rather than precise factors. At depth seven neither caveat applies:
the engine takes $\CoreDeepMs$\,ms against $\AuthorityDeepSeconds$\,s, so that row is a direct measurement on both sides.

Each side is timed at its interface. \texttt{MultiwaySystem} is the implementation a user
would otherwise run, timed through its exposed properties; every property it exposes is
graph-valued (\texttt{StatesGraph}, \texttt{CausalGraph}, \texttt{EvolutionGraph} and their
siblings), so no interface returning the state set alone
is available and its time necessarily includes building Wolfram \texttt{Graph} objects. The
engine appears twice: at its native C++ API, and reached through the paclet the way a Wolfram
user reaches it, with WXF serialization to the worker process, evolution, and the same kind of
Wolfram structures built on return. The gap between those two columns is the Wolfram layer
measured on this project's own engine, with the computation held fixed: at depth
\SpeedupHighDepth{} the layer turns $\CoreDeepMs$\,ms into $\PacletDeepSeconds$\,s, a factor of
$\PacletOverheadDeep\times$, so no speed claim in this paper is taken through it; the
native interface is where the computation's own cost is visible, and even under the layer the
engine remains $\PacletVsAuthorityDeep\times$ ahead of the authority on the like-for-like
basis. The \emph{Counts agree}
column requires the authority, the engine and the reference to have produced the same state and
causal-edge counts at that depth, since a timing comparison between different state spaces is
not a comparison, and they agree exactly at every depth.

\subsection{Quotient Exploration (Table T6)}
Quotient exploration expands each canonical state once, at its shortest reachable depth, so the
number of events actually produced grows far more slowly than the raw count; full expansion and
quotient exploration produce the same canonical state set, and the columns report the difference
in events produced and in wall time. At depth seven the quotient arm produces $28$ events where
full expansion reaches $5{,}913$, and reconstruction recovers all $5{,}913$, with their causal
edges and branchial pairs, exactly from those $28$; the \emph{Exact} column is a per-row
verification, not a description. Reconstruction's own cost is below the resolution of this
measurement: the \texttt{quot.+recon} column lands at or under the \texttt{quot.} column at most
depths, which is run-to-run variation on sub-millisecond timings and not a negative cost. The
table establishes that reconstruction is exact and cheap enough not to register beside the
evolution it reconstructs from; pricing it would need a workload large enough to separate the
two. The saving is in what is expanded, not in what is reported.

\subsection{GPU (Table T7)}
The device is not uniformly faster, and the range over which it is faster has both ends
(Figure~\ref{fig:gpu}). Both sides run the same rule, initial condition, canonicalization mode
and exploration strategy, and report medians from a single session on the machine in the
table's provenance line; branchial edges are constructed through a per-(state, edge) index. At
depth five the CPU wins, because the work per launch does not amortize the cost of getting it
there; from depth six the device is ahead of both CPU columns and the margin widens with depth,
reaching $\GpuSpeedupAtDeepest\times$ eight CPU threads at
depth $\GpuDeepestDepth$; against a single thread the factor is larger still (Table~\ref{tab:t7-gpu}).

The resident-kernel design has its own boundary, on the same workload and measured by the same
tool (Table~\ref{tab:t16-persistent}). Against a conventional per-step \texttt{evolve()} the persistent evolver is $\PersistentSpeedupFour\times$
faster at depth four, $\PersistentSpeedupFive\times$ at five, $\PersistentSpeedupSix\times$ at six and $\PersistentSpeedupSeven\times$ at seven, and
$\PersistentSpeedupEight\times$ at depth eight and $\PersistentSpeedupNine\times$ at nine, where the two are indistinguishable. The
advantage is the elimination of a fixed per-call cost, which is visible directly in the
\texttt{evolve()} column: it is $\PersistentEvolveConstLo$--$\PersistentEvolveConstHi$\,ms at depths four, five and six, almost independent of
a state count that grows from $\PersistentStatesLo$ to $\PersistentStatesHi$ over that range. Once the evolution itself is large
enough to dominate that constant (by depth \PersistentTieDepthWord, at $\PersistentStatesTie$ states), keeping the kernel
resident removes nothing further, and the two designs are indistinguishable: at depths eight and
nine the ratio reads $\PersistentSpeedupEight\times$ and $\PersistentSpeedupNine\times$, inside the
run-to-run variation of Section~\ref{sec:benchmarks}. Reporting the speedup without the depth it is measured at
would therefore be a statement about small problems.

\subsection{Parallel Efficiency by Rule Shape (Table T12)}
The rule set decides how much parallel work exists, so a scaling curve characterizes the rule as
much as the engine. Two shapes are measured at every thread count: a one-edge left-hand side,
which re-matches by scanning an index and expands each state narrowly, and a two-edge left-hand
side, which joins and produces a wider frontier. With both shapes sized to seconds of
single-threaded work, their efficiency curves lie within a few points of each other at every
thread count (the floor across the two is $\EffAtEight$ at eight threads and $\EffAtSixteen$ at
sixteen), and both keep improving in wall time through thirty-two threads. The difference in how
they match, an index scan against a join, does not separate their scaling once each carries
comparable work; what governs both is the cross-domain term of
Section~\ref{sec:benchmarks}'s memory analysis, which the every-thread-count sweep locates at
the first step that opens a second L3 domain. The decline is not thread setup: both serial
points are seconds, not milliseconds. The table gives the wall times behind the size axis of
Figure~\ref{fig:lhs-scaling}; Section~\ref{sec:lhs-space} sweeps the same axis at four sizes
and two further properties of the left-hand side.

\subsection{Left-Hand-Side Properties}
\label{sec:lhs-space}

Table~\ref{tab:t12-shapes} varies one property of the rule, the edge count of its left-hand
side, and holds two others fixed without naming them. A left-hand side has three
independent properties, and each changes the matching problem in a different way:

\begin{itemize}
\item \textbf{Size}: the number of edges to bind. Each additional edge is another factor in
      the search, and another constraint that prunes it.
\item \textbf{Arity}: the number of vertices per edge. Arity changes how much of the state a
      single edge determines once bound, without changing how many edges must be found.
\item \textbf{Connectivity}: how the edges share vertices. A path shares one vertex between
      consecutive edges; a star shares one vertex among all of them; a ring has no endpoint
      to anchor at; and a left-hand side whose components share \emph{no} vertex cannot be
      joined at all, so it is matched by enumerating a cartesian product: quadratic in the
      state size for two components, and worse for more.
\end{itemize}

Figure~\ref{fig:lhs-scaling} sweeps each axis separately, and the result on the first axis runs
opposite to the intuition that a larger pattern is harder to parallelize. Parallel efficiency at
32 threads \emph{rises} monotonically with left-hand side size: $0.15$, $0.49$, $0.67$, $0.73$
for one, two, three and four edges. The one-edge rule is the worst-scaling shape measured, and it
is not scaling badly for want of work: across the four chain sizes of this figure its serial time
is the largest. It runs $17.9$\,s, against $5.7$, $10.3$ and $12.7$\,s for two, three and four
edges. (Table~\ref{tab:t12-shapes} sweeps two different rules at different depths, so its serial
column is not comparable with these.) A one-edge pattern binds one edge per match, so the work
between two synchronizations is small and the fixed cost of publishing a state dominates; each
further edge adds join work per match without adding a synchronization.

Connectivity moves the curve much further than size does, and in both directions. At 32 threads
the ring reaches $1.06$ and the branching tree $0.96$ (superlinear, because a wider frontier
lets workers deduplicate states that a serial order would expand), while the path and the hub sit
at $0.67$ and $0.62$. The disconnected shape reaches $0.06$: seventeen times worse than the ring
on the same machine and the same thread count. That is the widest spread in the whole sweep, and
it is the reason connectivity rather than size is the property to state when a rule set's scaling
is being predicted. The disconnected case is reported here rather than in a section of its own,
because it is this same axis taken to its limit. Its cost is also not only the cartesian product:
on a processor whose cores do not share one last-level cache it is dominated by coherence traffic.
Measured on the evaluation machine at a fixed two threads, so scheduling and work distribution are
held constant, the same disconnected workload takes $976$\,ms when both threads share an L3
instance and $1494$\,ms when they do not, against $1322$\,ms on one thread: two threads that share
a cache speed it up, two that do not are slower than serial.

Edge arity is the weakest axis in one direction and not in the other. At a fixed three-edge
left-hand side, efficiency at 32 threads is $0.67$ at arity two, $1.015$ at arity three and
$0.777$ for a left-hand side alternating arities two and three. Raising the arity of a path raises
the overlap between consecutive edges from one vertex to two, which pins a match's orientation
and removes the second way of binding it; the resulting frontier is narrower per state and
deduplicates more, which is where the superlinear value comes from.

\subsection{Evolution Depth and Relation Sizes}
\label{sec:shape-space}

Each shape is evolved one depth at a time until a single run exceeds the collection budget, so
the right-hand end of each curve in Figure~\ref{fig:shape-space} is a measured boundary for
that shape rather than a depth chosen in advance for all of them. Runs that reached a container
ceiling are excluded: the engine returns a truncated graph with a warning when a container
fills, and such a run reports where it filled rather than how large the state space is.
Measured, one shape totals the same $2{,}097{,}149$ states whether asked for depth 9, 10 or 11,
redistributing that ceiling over however many levels were requested. Of the $192$ collected

Wall time is one property of a workload and the sizes of the objects it constructs are another.
Two runs can agree on state count and still differ by more than an order of magnitude in the

\subsection{Memory Behavior under Thread Scaling (Table T13)}
A falling efficiency curve does not say which resource is being consumed, and the two candidates
imply opposite remedies: changing the shared structures would fix contention on them, but not
the cost of the memory the run acquires. Both are read from
\texttt{getrusage} on the same runs. Across a $\ThreadSweepFactor\times$ increase in worker
count, user time increases by a factor of $\UserTimeGrowth$ while system time increases by
$\SysTimeGrowth$ and stays below three seconds of a hundred and twenty-eight: the cost sits in
user time. It is not spinning, because the instruction count is flat across the sweep (the
paragraph that follows), and it is not memory acquisition, because the peak resident set grows
by a quarter across the sweep while the minor-fault count grows eleven-fold: the kernel term
tracks the faults, which come from each worker drawing its own arena blocks, and it stays
small. Wall time keeps falling through thirty-two threads on this workload while user time
grows seven-fold, so the added workers are busy, and what they are busy with is the
cross-domain traffic the next paragraph measures. The result is specific to the host: a part
with larger L3 domains would place the two terms differently.

A second term sits in user time, and hardware counters separate it from both candidates above.
On the Wolfram rule at depth seven the instruction count is flat across the sweep ($14.5$G at
one thread, $15.8$G at 32) while cycles double, so instructions per cycle falls from $1.44$ to
$0.69$; the growing counter is demand fills served from \emph{another} L3 domain's cache
(AMD \texttt{ls\_dmnd\_fills\_from\_sys.near\_cache}), $47$k at one thread to $10.6$M at 32,
while fills from DRAM and from the local hierarchy stay flat. Two experiments exclude the
concurrent structures as the source: capping the shared table's probe length from $32$ to $4$
leaves the fill count unchanged while wall time grows, and an exact thread-private filter that
removes $80\%$ of the repeated shared-set insertions moves the set's share of the fills from
$36\%$ to $12\%$ without moving the total or the wall time; the traffic re-attributes to the
neighbouring sites. The term is therefore the data flow of the evolution itself, about twelve
cross-domain fills per object created: a state produced on one core complex is consumed on
others, and on a part with eight separate L3 domains those reads are served across domains.

The term is visible without counters at the point where it first appears. Sweeping every
worker count from one to thirty-two, with workers pinned in order across a part whose L3
domains hold two cores each, wall time falls from one worker to two and \emph{rises} from two
to three on every large workload (\texttt{wpp} by $12.7\%$, \texttt{wolfram24} by $20.4\%$,
\texttt{wolftri} by $12.8\%$, \texttt{multirule} by $36.1\%$), before falling again from four
onward. The third worker is the first to sit on a second L3 domain, and the traffic it opens
costs more than its share of the work. Pinning that third worker to an SMT sibling inside the
first domain instead removes the rise (\texttt{wpp} $347$ to $258$\,ms at three workers,
below the two-worker time) and moves the same step to the fourth worker, where the second
domain opens: the cost belongs to opening a domain, not to a count. Packing each domain's two
cores and two SMT siblings before opening the next is faster at every count measured,
including sixteen (\texttt{wpp} $197$ to $182$\,ms, \texttt{wolfram24} $36.3$ to
$33.3$\,ms, \texttt{multirule} $34.7$ to $25.7$\,ms), so on this topology halving the number
of L3 domains a run touches is worth more than doubling its physical cores. The packed
placement is the engine's own default, derived at start-up from the cache topology the
operating system reports, and it is the placement the tables in this section were measured
under; the one-per-physical-core order is the counter-example, measured here by naming the
CPUs explicitly. Under the engine's placement the step moves to where the first extra domain
opens: on this part a domain holds four hardware threads, so the fifth worker is the first on a
second domain and \texttt{wpp} runs $216$\,ms at four workers, $247$ at five, $234$ at six and
$205$ at eight, after which every further domain opens with the term already amortised (the
largest later rise across one to thirty-two workers is $2.3\%$). No placement of a fifth
worker on two-core domains avoids that step, so the supported worker counts on such a part
are the powers of two, at which the curve is monotone, and the every-count sweep is the gate
that states it.

\subsection{Occupancy and Lane Efficiency}
\label{sec:device-bounds}

Table~\ref{tab:t11-saturation} establishes saturation behaviorally and states that its final column is not an occupancy figure. This section supplies the occupancy figure and the second bound that sits beside it, both read from the shipped binary rather than inferred from timings, so that the device results above are reported against the ceilings they were measured under.

Two resources bind the resident kernel, and they multiply rather than compete.

\textbf{Registers.} Reading the linked binary with \texttt{cuobjdump -res-usage}, \texttt{k\_persistent\_evolve} is allocated 255 registers per thread, which is the architectural maximum. The kernel is launched with 32 threads per block, so a block reserves $255 \times 32 = 8{,}160$ registers; a streaming multiprocessor on the sm\_89 part used here provides 65{,}536, admitting eight resident blocks, or 256 threads against a hardware maximum of 1{,}536. Occupancy is therefore $16.7\%$, and it is register-bound rather than bound by shared memory (48 bytes per block) or by block count. Per-translation-unit object files report no stack or local frame for any function under separate compilation (\texttt{-rdc=true}); only the linked binary carries the allocation, and reading the intermediate objects understates it to zero.

\textbf{Lane efficiency.} The canonicalization stretch of the kernel, the phase the measurements below show to dominate, runs on the whole warp: every lane enters the shared canonicalization core together under an execution policy, the order-safe loops of refinement fan across the lanes, and the search's serial trunk (individualization, the orbit closure on return, the backjump) executes on the leader behind warp barriers while the other lanes hold the same control flow. The publication, signature, quotient and deduplication steps that follow it run on the leader alone. The achieved width is measured rather than derived: on \texttt{wpp} at depth six the profiler reports $3.5$ active threads per warp averaged over the kernel, against a ceiling of $32$ (Table~\ref{tab:device-occupancy}). That average is the two regimes weighted by their cycle share, and the serial trunk is the larger share.

Hardware counters exclude every memory and arithmetic alternative, and a direct experiment excludes occupancy itself. No unit is near its limit: on \texttt{wpp} at depth six SM throughput is $9.7\%$ of peak, memory throughput $24.3\%$ and DRAM $11.6\%$, and across the corpus the maxima are $12.6\%$, $33.8\%$ and $16.1\%$ (Table~\ref{tab:device-occupancy}). Atomic traffic, which the work queues make the natural suspect, lands in L2, whose throughput sits at that memory figure, leaving several times' headroom.

Occupancy requires more care than the register figure alone suggests, because two independent limits coincide. The resident kernel is allocated 255 registers, which over a 32-thread block permits eight blocks per streaming multiprocessor; the kernel is also launched with a grid of eight blocks per multiprocessor. Both give eight warps of a possible forty-eight, or $16.7\%$, and the measured occupancy of $16.7\%$ on \texttt{wpp} (Table~\ref{tab:device-occupancy}) is consistent with either. They are separable by experiment. Capping the whole device library at 128 registers halves the allocation and leaves occupancy unchanged, so the register ceiling was never the binding constraint; raising the grid with that cap in place doubles residency and makes the kernel \emph{slower}, degrading further as the grid grows. This is consistent with the behavioral saturation of Table~\ref{tab:t11-saturation} and identifies its cause: additional resident warps contend for the shared work cursors without contributing independent work.

The device is therefore limited neither by bandwidth, nor by queue contention, nor by occupancy. It is limited by the dependency structure of the work itself. Individualization--refinement is a depth-first backtracking search in which each step depends on its predecessor, and no quantity of resident parallelism executes a dependent chain faster. The scans over vertices and edges are the loops the warp fans; the search itself fans nothing. With the scans distributed, the phase's remaining cost is the chain, and the chain is the device's ceiling for this algorithm on this architecture: a property of canonicalization rather than of the implementation.

Taken as a product, a small fraction of the device's arithmetic capability is reachable by the dominant phase. The measured throughput reflects that bound, and it is a structural property of the current work decomposition rather than a scheduling artifact or a stall: an independent instrument (below) reports zero time spent waiting on unpublished work.

Per-phase attribution, taken from \texttt{clock64} deltas accumulated per block and summed at exit, locates the cost: on the corpus workloads that generate enough work to attribute anything, canonicalization takes the large majority of block cycles, rewriting a few per cent and matching under two. The remaining corpus shapes produce between four and $1{,}409$ states at depth six (Table~\ref{tab:t7b-gpu-corpus}) and are idle most of the time; that is the absence of work rather than a property of the scheduler, and their idle fraction should not be read as a device inefficiency. Canonicalization is thus both the dominant phase and the phase whose serial trunk sets the lane average, and the two bounds above identify the same site in the code by independent routes.

A third bound sits outside the kernel, in the per-call bracket rather than in the evolution itself. Tracing a device run and placing every allocation and copy relative to the resident kernel's own execution: no copy, allocation or memset occurs while the kernel is running (the count is zero across every evolution measured), so the evolution proper is free of host traffic, as the design requires. The bracket around it is not: each evolution's kernel is preceded and followed by runtime allocation, copy and fill calls, in equal numbers on the two sides of the launch. The design goal of a single readback at the end is therefore not met, though the stronger property of no traffic during evolution is. This bounds interactive and session use, where a caller pays that bracket on every call, rather than throughput on a single deep run, where it is amortized over the kernel's duration.


\paragraph{Causal recording.} The reconstruction of the raw causal and branchial relations is selectable independently of the evolution, and the measurements reported so far switch all of it off. Re-measured with causal recording on, the device and host agree \emph{exactly} on the reconstructed relation for the eight corpus workloads the device backend supports, at depth six: identical distinct-pair counts and identical counts surviving transitive reduction. The two implementations share no code below the shared replay core, so the agreement is between two separate schedulers, memory layouts and queueing disciplines. On the densest workload available, a three-edge disconnected left side at depth three, the two engines agree on $1{,}661{,}760$ causal pairs and $970{,}560$ surviving reduction.

Reaching that agreement is a property of how the reduction is defined rather than of how it is computed. A finite directed acyclic graph has exactly one transitive reduction, so membership is a function of the finished relation; both engines therefore store the relation and reduce it on demand, rather than deciding each pair as it arrives against the pairs seen so far. The two engines share that body. Deciding on arrival makes the answer depend on the schedule: a pair reaching the relation before the longer path that bypasses it is kept, the same pair reaching it afterwards is dropped, and an append-only adjacency never retracts the difference. The reduction is computed once per source rather than once per pair (every edge leaving a given event shares the set reachable from it in two or more steps), and where event identifiers increase along every causal edge the search is bounded by the largest target of that source. The branchial relation is handled the same way: a branchial pair is two applications of one instance sharing a consumed slot, so neither engine stores the pairs, and both derive them from the applications on demand.

\paragraph{Idle fraction under causal recording.} The attribution above reads the idleness of the corpus shapes producing few states as work not existing. With causal recording on this reading no longer holds for two of them: at depth six \texttt{cycle4} and \texttt{multirule} reconstruct causal relations orders of magnitude larger than their state counts, and both remain almost entirely idle. Hardware counters place them far from every ceiling (SM throughput $2.2\%$ of peak and DRAM $0.01\%$ on \texttt{cycle4}, Table~\ref{tab:device-occupancy}), and their lane efficiency is among the corpus's best, $9.8$ and $10.4$ of $32$, against $2.7$ on \texttt{wolfram24}, which the device completes faster than sixteen host threads (Table~\ref{tab:t7b-gpu-corpus}). The decisive comparison is that the kernel takes four times longer on \texttt{multirule}'s $49$ states than on \texttt{wolfram24}'s $9{,}820$.

What separates the two regimes is the parallel width, and the corpus supplies a controlled comparison for it. At depth six \texttt{cycle4} replays $68{,}185$ instances over $40$ classes and loses to the host; \texttt{wolfram24} replays $86{,}086$ over $9{,}820$ classes and beats it (Table~\ref{tab:t7b-gpu-corpus}). The instance counts are within $30\%$ of each other and the outcomes are opposite, so neither the amount of replay work nor the depth of the recursion is the discriminator. The state count is: a class is the unit over which the replay's instances are independent, and a run that collapses to forty classes has forty-fold width available however much work those classes carry. \texttt{cycle4} begins from a deliberately automorphic initial state, which is exactly the condition that collapses classes. The device's disadvantage on these shapes is therefore a shortage of independent work rather than an inability to execute the work it has, and raising occupancy against it would raise the idle count rather than the throughput.

The instances \emph{within} a class can be replayed concurrently. They are serialized by the worklist:
each driver takes its instances from a
worklist private to it, so a class is walked by one driver and, on a run that collapses to forty
classes, forty such walks proceed while the remainder of the grid spins.

The instance count and the class count are far apart on exactly the shapes that lose. At depth six \texttt{cycle4} materialises
$68{,}185$ instances over $40$ classes and \texttt{multirule} $146{,}599$ over $49$ (ratios of
$1{,}705\times$ and $2{,}992\times$), while \texttt{wolfram24} materialises $86{,}086$ over
$9{,}820$ and \texttt{wpp} $15{,}967$ over $3{,}867$, ratios of $8.8\times$ and $4.1\times$. The
instance counts are comparable across all four, between $16$ and $147$ thousand, while the class
counts vary by a factor of $250$: the independent work available is similar everywhere and only the
width the implementation exploits differs. The shapes that lose are those whose initial state
collapses classes, and that collapse is the same condition that concentrates instances into few of
them.

The residual on these two workloads is accordingly attributed to a named and evidenced cause: the replay's depth-first descent runs inline on the discovering thread, so a class's instances are walked by one driver, and a run that collapses to forty classes has forty drivers' worth of width however many instances those classes carry. That is a bound of the replay's work decomposition, stated as measured, and it is not claimed as a lower bound on the problem.

\paragraph{Measurement bounds.} Nothing in this corpus is near a hardware ceiling: across the profiled corpus the highest SM-throughput figure is $12.6\%$ of peak (\texttt{wolfram24}) and the highest DRAM figure $16.1\%$ (\texttt{growshrink3}) (Table~\ref{tab:device-occupancy}). Occupancy is structural for the reason given above. The lane average separates the two regimes: about three lanes per warp on the large-state workloads, where the canonicalization trunk binds, and nine to twelve on the shapes of at most forty-nine states, where the shortage of independent work binds; \texttt{disc2x2}, \texttt{arimix} and \texttt{multiroot} sit between, at six to nine. The allocation invariant holds with the reconstruction running as well: profiling twenty-four consecutive evolutions records zero allocations, copies or memsets between a resident kernel's start and its end, with every such call falling in set-up or read-back. What is not established is whether the serial chain is irreducible; it is attributed and bounded, not proven minimal.

The quotient decoupling of Section~\ref{sec:quotient} applies to the device on the same terms as the host. Capture of each class's frame is separated from replay of that capture against instances. The first signs event identity at the cost of the canonical answer, the second recovers the raw event set at the cost of the raw one. Together they leave the canonical answer bit-identical while removing the exponential from runs that do not request raw events. Two corpus shapes, \texttt{multirule} and \texttt{cycle4}, do not complete depth seven under unconditional replay at all; with capture and replay separated both complete, with state and event counts identical in the two arms, and the step from depth six to seven costs almost nothing further where the unconditional arm does not terminate.

Two routes around the canonicalization bound were measured and rejected. Both are reported here because they bound the same quantity from two sides, and because the two fail for opposite reasons. Tiered canonicalization (bucket by the Weisfeiler--Leman signature, run individualization--refinement only on a collision) was implemented and measured at $28\%$ slower, because a bucket hit still requires refinement to confirm isomorphism, so a duplicate state is processed by both stages. A content-equality short-circuit reuses a canonical form when two raw states hold literally the same edge tuples. It needs no confirmation, being a proof of isomorphism on its own, and it never fires. Measured over \texttt{wpp}, the number of distinct state contents equals the number of raw states exactly at depths six and seven ($3{,}867$ of $3{,}867$; $45{,}317$ of $45{,}317$), because every rewrite mints fresh vertex identifiers, so no two states reaching one canonical form carry the same labels. The measurement is order-independent and therefore an upper bound on the catch available to any content key. The two routes fail oppositely: the first fires often but confirms redundantly, the second would need no confirmation but never fires. The $1.59\times$ gap between refinement passes performed and distinct canonical states is real; reaching it requires recognising isomorphic states without canonicalizing them, which is the problem canonicalization solves.

These figures hold across the corpus rather than on one shape. Profiling the resident kernel on every corpus workload (with the profiler rather than by wall clock, so that occupancy, throughput and the lane average are read from hardware counters rather than inferred from elapsed time) gives occupancy between $14.1\%$ and $17.3\%$ on every one, over workloads whose profiled kernel durations differ by a factor of seven hundred (Table~\ref{tab:device-occupancy}):

\paragraph{Per-phase lower bounds.} Each host phase is divided by the unit it produces once per item,
read from the same run's counters: $\InstrIrCalls$ canonicalization calls over $\InstrRaw$ raw
states, $\InstrEvents$ reconstructed events, $\InstrSetInserts$ claim-set inserts and

$\InstrCanonHashPct\%$ in the per-call set-up and invariant hash around it, and
$\InstrCanonOrbitsPct\%$ in the orbit computation the quotient's event identity requires.
Reconstruction costs $\InstrIrPerReconEvent$ instructions per reconstructed event against a floor
of one identity claim, a producer lookup per consumed edge and a producer record per produced
edge, a few hundred instructions for a two-in, four-out rule; the excess sits in the per-instance
replay descent (\texttt{qr\_apply}) and in \texttt{register\_quotient\_transition}'s vector
traffic. The claim sets cost $\InstrIrPerSetInsert$ instructions per insert against a floor of
one hash, one probe and one exchange, around fifty; $\InstrSetRepeatPct\%$ of the inserts offer a
key the set already holds and pay the probe for nothing. Matching, the join and the rewrite cost
$\InstrIrPerAppliedMatch$ instructions per applied match, a figure that includes building the
match record and the child state, so its floor is the child's construction rather than the two
edge bindings. No host phase is within a factor of two of its floor, and each excess is
attributed above to a named site. The libc share is copies, fills and heap traffic; the raw
profile attributes its largest callers to the benchmark's own set-up, inlined into
\texttt{main} under link-time optimisation, and to the construction of rule objects.

\subsection{Event Canonicalization Overhead}
Event identity is not one convention but three, and they disagree in general rather than in
corner cases. Table~\ref{tab:event-canon} evolves each workload once, under \textsc{Full} state
canonicalization and single-threaded, and counts the distinct events under each: identifying an
event by its endpoint states, by the edges it consumed and produced, and by the distinct rule
applications. The conventions refine one another (two rewrites are the same event when they run
between the same states, when they additionally move the same edges, or never), so the counts
are non-decreasing left to right, and where they strictly increase the finer convention
separates rewrites the coarser one merges. On \texttt{binary-growth} the three give $5$, $8$
and $9$. The table carries no timing column: what separates the conventions is what they
identify, and the cost of the identity is the added canonicalization pass
Table~\ref{tab:t9-ablation} measures. A paper reporting an event count must therefore say which
convention it used, and this one uses the canonical convention throughout.

\subsection{Limitations}
\label{sec:limitations}

\textbf{Single machine.} All numbers were taken on one desktop, whose configuration is given in
Section~\ref{sec:benchmarks} and repeated in each table's provenance line. The scaling results in
particular are properties of this machine's memory system and core count, and the thread count at
which efficiency declines is not portable to a machine with a different one.

\textbf{Quotient reconstruction scales with the system it avoids visiting.} Quotient exploration
visits one representative per isomorphism class, and its state count can grow far more slowly than
the raw system's. The reconstruction that recovers raw observables from those representatives does
not share that saving: it materialises instances, and there are as many instances as the raw system
holds. Measured on a two-rule set whose canonical state count grows linearly with depth, the
reconstruction's cost grew about twentyfold per step: 0.17, 0.22, 0.62, 7.36, 144.78 and 4981.05
milliseconds at depths two through seven for three, four, five, six, seven and eight canonical
states. The growth rate is a property of the output rather than of the implementation: the raw
observables are as numerous as the raw system holds, whatever computes them. The cost applies only
to runs that request those observables. The reconstruction is enabled by the request, so a run
asking for canonical states alone does not perform it.

\textbf{The reconstruction does not scale with threads.} Every worker drives it, and the total
cycles it consumes grow with the thread count: 511 million cycles on one thread against 3.85
billion on thirty-two for the same admitted work, measured on the densest reconstruction
workload in the corpus. The dedup marks prevent duplicate effects but not duplicate traversal,
so added threads contend rather than divide the work. On that workload wall time improves to
eight threads and degrades beyond it; the corpus rows whose reconstruction is small do not
reach the regime where the effect is measurable.

\textbf{Two comparison points, one of them our own.} The implementations compared against are the
\texttt{Wolfram/\allowbreak Multicomputation} paclet's \texttt{MultiwaySystem} and this project's own
reference implementation. The first is the only external implementation known to us that computes
the deduplicated states graph under an isomorphism identity; SetReplace computes a different
object (Section~\ref{sec:background}), so no wall-time comparison against it is reported. The
second is written by the same author as the engine, from the same definition, which makes it an
independent implementation of the definition but not an independent party's implementation.

\textbf{Workload scope.} Two corpora are used and they are different sizes. The oracle corpus
is 17 rule-type workloads and is what Tables~\ref{tab:t1-exactness},
\ref{tab:t3-deheap} and~\ref{tab:event-canon} report; the left-hand-side sweep of
Section~\ref{sec:lhs-space} generates 24 shapes of its own, reported by
Table~\ref{tab:t14-shape-space}. Both were constructed to cover rule
shapes (productive, reductive, idempotent, mixed arity, disconnected and
high-automorphism) rather than to sample rules found in practice, and the observed behavior of
$C/R$ and of parallel efficiency is a property of those shapes.

\textbf{Scope of the concurrency results.} The model-checked properties hold for the thread and
operation counts given, which are small; they are not proofs for unbounded thread counts. The
determinism gate likewise establishes agreement across the configurations it runs, not for all.

\textbf{Worst-case cost.} Individualization--refinement is exponential in the worst case, and the
exact mode applies it to every state. States with large automorphism groups are where that cost is
realized, and Proposition~\ref{prop:wlceiling} shows that a cheaper pre-filter cannot avoid it.
